## Как читать справочник

Для каждой команды указаны:

- **Класс** — файл в `app/Console/Commands`.
- **Назначение** — что команда делает по шагам и какие таблицы затрагивает.
- **Опции/аргументы** — если есть.
- **Расписание** — запускается ли автоматически (см. `bootstrap/app.php`).
- **Безопасность** — есть ли режим `--dry-run`, резервные снимки, риски перезаписи данных.

Общие соглашения проекта:

- Команды с `--dry-run` и `--apply` требуют явно указать ровно один режим — по умолчанию ничего не пишется в БД.
- Тип источника определяется полем `api_channels.is_company` (`ApiDataTypeEnum`): `Builder` — строители, `Specialist` — проектировщики, `Company` — вакансии.
- Статус ИИ-обработки поста — `api_channel_posts.ai_parse_status` (`ApiChannelPostStatusEnum`): `InQueue`, `Complete`, `Error`, `Empty`, `DontMatch`, `Duplicate`.

## 1. Парсинг источников (Telegram / VK)

Читают новые сообщения из подключённых каналов и складывают их в `api_channel_posts` со статусом `InQueue`, после чего посты забирает ИИ-обработка.
Обрабатываются только каналы со статусом `Active` и соответствующим `is_company`.

### `app:tg_parse:builder`

- **Класс:** `ParseTelegramBuilderChats`
- **Назначение:** парсинг Telegram-каналов типа «Строитель» через MadelineProto. Все каналы читаются в рамках одной общей сессии (`readTelegramChannelsWithSharedSession`), сообщения сервиса `ReadTelegramChats` выводятся в консоль.
- **Расписание:** да (см. раздел про cron).
- **Требует:** авторизованную сессию MadelineProto (`app:tg_auth`).

### `app:tg_parse:specialist`

- **Класс:** `ParseTelegramSpecialistChats`
- **Назначение:** то же самое для каналов типа «Проектировщик/Специалист».
- **Расписание:** да.

### `app:tg_parse:company`

- **Класс:** `ParseTelegramCompanyChats`
- **Назначение:** то же самое для каналов типа «Вакансия/Компания».
- **Расписание:** да.

### `app:vk_parse:builder`

- **Класс:** `ParseVkBuilderChats`
- **Назначение:** чтение стен VK-сообществ (сервис `ReadVkGroups`) для каналов типа «Строитель». Каждый канал обрабатывается последовательно, результат печатается в консоль.
- **Расписание:** да.

### `app:vk_parse:specialist`

- **Класс:** `ParseVkSpecialistChats`
- **Назначение:** то же для VK-источников типа «Сотрудник/Проектировщик».
- **Расписание:** да.

### `app:vk_parse:company`

- **Класс:** `ParseVkCompanyChats`
- **Назначение:** то же для VK-источников типа «Вакансия».
- **Расписание:** да.

## 2. Обработка постов через ИИ

Забирают до 100 постов со статусом `InQueue` за запуск, отправляют в ИИ (YandexGPT или Ollama Qwen — по настройке канала `api_ai`), создают карточки и выставляют пост в `Complete` / `DontMatch` / `Error`.

### `app:ai_parse:builder`

- **Класс:** `AiBuilderPosts`
- **Назначение:** самый сложный пайплайн проекта — превращает пост строителя в карточку `Builder`. Основные шаги:
  1. Проверка, что ИИ канала активен, выбор провайдера (`ApiAIYandex` / `ApiAIOllama`).
  2. Ранний редирект: если текст относится к проектированию/визуализации/дизайну, пост уходит в каталог проектировщиков (`BuilderNonFieldSpecialistRedirect`).
  3. Для Ollama при включённом двухпроходном режиме — Pass 1 (`BuilderServiceOfferClassifier`): мусор и не-услуги сразу получают `DontMatch`.
  4. Pass 2: промпт канала (или дефолтный) + подстановка списка специализаций, разбор JSON-ответа.
  5. Нормализация типа, формы собственности, типов объектов, техники (`BuilderNormalizer`); эвристика подработки/найма может переопределить «услугу» на «вакансию» → `DontMatch`.
  6. Подбор специализаций (`BuilderSpecialityMatcher`) по тексту и ответу ИИ, нормализация региона (`RussianRegionNormalizer`).
  7. Эвристики не-услуги (`CatalogPublicationBuilderNonServiceSignals`) и «гейт публикации» (`CatalogPublicationGate`) решают: `DontMatch`, автопубликация или модерация.
  8. Создание `Builder`, синхронизация специализаций автора, создание алерта модерации.
- **Важный риск:** повторная обработка удаляет и создаёт карточку заново (`delete` + `create`), поэтому ручные правки в карточке теряются.
- **Логи:** `ai_debug`, `builder_type_override`, `catalog_publication_gate`.
- **Расписание:** да, каждые 30 минут.

### `app:ai_parse:specialist`

- **Класс:** `AiSpecialistPosts`
- **Назначение:** обработка постов проектировщиков. Логика вынесена в сервис `SpecialistPostImporter`, команда лишь выбирает посты, готовит провайдера и печатает результат импорта (`created`, `dont_match`, `no_prompt`, ошибка).
- **Расписание:** да, каждые 30 минут.

### `app:ai_parse:company`

- **Класс:** `AiCompanyPosts`
- **Назначение:** обработка постов с вакансиями. Принимаются типы «вакансия», «поиск того кто окажет услугу», «поиск подрядчика» — остальное `DontMatch`. Создаёт `CompanyJob` со статусом `Active`, подбирает специализации по словарю и ставит алерт модерации.
- **Расписание:** да, каждые 30 минут.

## 3. Возврат постов в очередь ИИ (переобработка)

### `app:ai_parse:requeue`

- **Класс:** `AiRequeuePosts`
- **Назначение:** универсальная команда повторного прогона сообщений через ИИ. Заменила ранее существовавшие `app:ai_parse:reset-builder-queue` и `app:ai_parse:reset-specialist-queue`. Возвращает выбранные посты в `InQueue` и (по умолчанию) ставит фоновую обработку в очередь Laravel.
- **Опции:**
  - `--type=all|specialist|builder|company` — тип источников.
  - `--status=unprocessed` — `unprocessed` (Error+Empty), `all` (плюс DontMatch и Complete) или явный список: `error,empty,dontmatch,complete,duplicate`.
  - `--from=Y-m-d` / `--to=Y-m-d` — период, указываются только вместе.
  - `--date-field=ai_date|post_date|created_at` — по какому полю считается период.
  - `--provider=` — фильтр по `ai_provider_used`.
  - `--keep-metadata` — не обнулять `ai_result`, `ai_date`, `ai_provider_used`.
  - `--no-dispatch` — только вернуть в очередь, без запуска фоновой обработки.
  - `--dry-run` — показать количество и распределение статусов без изменений.
- **Требует:** для фоновой обработки — запущенный `queue:work`.
- **Расписание:** нет, ручной запуск.

### `app:ai_parse:requeue-builder-missing-visible-posts`

- **Класс:** `AiRequeueBuilderMissingVisiblePosts`
- **Назначение:** точечное лечение «пустых карточек» в публичном каталоге строителей. Находит авторов каталога, у которых нет ни одного активного `Builder` с постом в статусе `Complete` и непустым текстом, и возвращает их посты в `InQueue`.
- **Опции:**
  - `--dry-run` / `--apply` — ровно один из двух обязателен.
  - `--limit=` — размер партии (посты берутся по возрастанию id).
  - `--status=` — какие статусы возвращать; по умолчанию `error,empty,dontmatch`, можно `*` (всё кроме Complete и InQueue) или числовые значения enum.
  - `--backup-dir=` — каталог JSON-снимка, по умолчанию `storage/app/ai-reprocess`.
- **Безопасность:** перед записью сохраняет JSON-снимок постов и связанных карточек (`requeue-builder-missing-<дата>.json`) для отката.
- **После запуска:** `php artisan app:ai_parse:builder`.

### `app:ai_parse:requeue-specialist-missing-visible-posts`

- **Класс:** `AiRequeueSpecialistMissingVisiblePosts`
- **Назначение:** полный аналог предыдущей команды для каталога проектировщиков (`PublicSpecialistCatalogScope`, модель `Specialist`). Набор опций и логика снимка идентичны, файл снимка — `requeue-specialist-missing-<дата>.json`.
- **После запуска:** `php artisan app:ai_parse:specialist`.

## 4. Мониторинг доступности ИИ-провайдеров

### `app:ai:health-check`

- **Класс:** `AiProviderHealthCheck`
- **Назначение:** проверяет все активные провайдеры Ollama (`api_ai` со статусом Active и источником Ollama Qwen) запросом `GET {host}/api/tags`. При недоступности отправляет алерт (`AiProviderHealthAlertService`), при восстановлении — уведомление о восстановлении. Возвращает код ошибки, если хотя бы один хост недоступен.
- **Настройки:** таймаут — `services.ai.health_check_timeout` (по умолчанию 10 с).
- **Расписание:** да, каждые 15 минут.

### `app:ai:yandex-health-check`

- **Класс:** `AiYandexHealthCheck`
- **Назначение:** проверяет YandexGPT реальным мини-запросом к `foundationModels/v1/completion` (5 токенов). Отдельно ловит случай незаполненных `API_KEY_TOKEN` / `Folder_id` в options провайдера. В алерт добавляется количество постов строителей, застрявших в очереди.
- **Расписание:** да, каждые 15 минут.

## 5. Каталог: специализации и качество карточек

### `app:catalog:sync_author_specialities`

- **Класс:** `SyncCatalogAuthorSpecialities`
- **Назначение:** пересчитывает специализации авторов публичного каталога по совокупности всех их сообщений с завершённой ИИ-обработкой, оставляя не более N специализаций на автора.
- **Опции:** `--dry-run`, `--only=both|specialists|builders`, `--max=3`.

### `app:builders:rematch_specialities`

- **Класс:** `RematchBuilderSpecialities`
- **Назначение:** пересчитывает специализации карточек `Builder` по тексту поста и (если сохранён) JSON-ответу ИИ через `BuilderSpecialityMatcher`. Изменённые записи затем синхронизируются на уровне автора.
- **Опции:** `--dry-run`, `--chunk=500`, `--only-empty` (только карточки без специализаций), `--builder=<id>` (одна карточка).

### `app:posts:speciality`

- **Класс:** `SpecialityPosts`
- **Назначение:** проставляет специализации карточкам, у которых их нет вообще: до 500 `Specialist` (по словарю) и до 500 `Builder` (через `BuilderSpecialityMatcher`) за запуск. Для затронутых авторов-строителей вызывает синхронизацию специализаций автора.
- **Расписание:** нет, запускается вручную по мере накопления карточек без специализаций.

### `app:catalog:disable-active-builders-hiring-text`

- **Класс:** `DisableActiveBuildersHiringTextCommand`
- **Назначение:** массовая чистка каталога строителей. Проходит по активным карточкам и проверяет текст поста эвристиками `CatalogPublicationBuilderNonServiceSignals` (найм, поиск исполнителя, не-услуга). Карточки с признаком «проектирование и т. п.» переносятся в каталог проектировщиков, остальные совпадения переводятся в статус «на модерации».
- **Опции:** `--dry-run` — только список совпадений с превью текста.

### `app:catalog:redirect-non-field-builders-to-specialists`

- **Класс:** `RedirectNonFieldBuildersToSpecialistsCommand`
- **Назначение:** целевой перенос активных карточек строителей с текстом про проектирование / визуализацию / дизайн в каталог проектировщиков: создаётся `Specialist`, карточка `Builder` удаляется. В итоге печатает статистику: найдено, перенесено (в т. ч. эвристикой без ИИ), отложено, ошибок.
- **Опции:**
  - `--dry-run` — только список совпадений.
  - `--requeue-if-no-ai` — при недоступности ИИ не применять эвристический fallback: пост остаётся `InQueue`, карточка строителя не удаляется.

## 6. Регионы

### `app:regions:normalize_stored`

- **Класс:** `NormalizeStoredRegions`
- **Назначение:** приводит поле `region` у всех `builders` и `specialists` к каноническому написанию по справочнику (`RussianRegionNormalizer`). Нераспознанные значения остаются как есть.
- **Опции:** `--dry-run`, `--chunk=500`.

### `regions:normalize-public-catalog-builders`

- **Класс:** `NormalizePublicCatalogBuilderRegions`
- **Назначение:** более жёсткий вариант только для карточек, попадающих в публичный каталог строителей: канон из справочника либо `NULL`, если регион не распознан. Использует тот же scope, что и публичный каталог.
- **Опции:** `--dry-run`, `--chunk=200`.
- **Обратите внимание:** имя команды без префикса `app:`.

### `app:sync_channel_region_to_posts`

- **Класс:** `SyncChannelRegionToPosts`
- **Назначение:** разовая миграция данных — проставляет регион канала во все `Builder` и `Specialist`, созданные из постов этого канала, у которых регион ещё пуст. Существующие значения не перезаписываются.
- **Опции:** нет, `--dry-run` отсутствует.

## 7. Каналы и инфраструктура Telegram

### `app:channels:enable-specialists`

- **Класс:** `EnableSpecialistChannelsCommand`
- **Назначение:** инвентаризация и включение отключённых каналов проектировщиков. Печатает таблицу (id, статус, источник, название, ссылка, привязанный ИИ, провайдер, статус ИИ) с предупреждениями «нет api_ai», «ИИ отключён», «не YandexGPT». При `--apply` переводит в `Active` только каналы со статусом `Disabled`; провайдер ИИ автоматически не меняется.
- **Опции:** `--dry-run` / `--apply` (ровно один), `--id=` (можно несколько), `--source=telegram|vk`, `--include-active` (показать активные в отчёте).

### `app:tg_auth`

- **Класс:** `AuthTelegram`
- **Назначение:** интерактивная авторизация MadelineProto в сессии `session.madeline.{api_id}` с теми же настройками прокси и Redis, что у парсера. Поддерживает вход по коду и по QR, запрашивает облачный пароль 2FA, корректно финализирует сессию и чистит IPC.
- **Опции:**
  - `--api-id=` / `--api-hash=` — иначе берутся `TG_APP_ID` / `TG_APP_HASH` из `.env` или `api_hash` активного канала с таким `api_id`.
  - `--qr` — вход по QR-коду (Telegram → Устройства → Подключить устройство).
  - `--reset` — архивировать битую сессию (например, при DC -1) и войти заново.
- **Перед запуском:** отключить cron с MadelineProto и завершить воркеры (`pkill -f "MadelineProto worker"`).
- **Проверка после:** `php artisan app:tg_parse:builder`.

### `app:tg_profile:photo`

- **Класс:** `TelegramProfilesPhoto`
- **Назначение:** дозагружает аватары профилей `api_post_users`, у которых `photo` пуст. Подключается через первый активный канал (нужны `api_id` и `api_hash` в его options), скачивает фото и сохраняет путь в БД. Ошибки по конкретному профилю не прерывают проход.

## 8. Рассылки

### `app:tg_chat:send_company`

- **Класс:** `SendMessageToTelegram`
- **Назначение:** приветственная рассылка в Telegram контактам компаний из раздела вакансий. Работает в двух режимах за один запуск: ручная рассылка (запланированное сообщение с наступившей датой отправки) и автоматическая (приветствие новым компаниям). Требует настроек `mailing_tg_api_id`, `mailing_tg_api_hash`; при выключенной настройке `mailing_tg_new_company` автоприветствия отключаются у всех ожидающих. Результат пишется в статус рассылки и лог-канал `mailing_tg`.
- **Расписание:** только если переменная окружения `SCHEDULE_TG_CHAT_SEND_COMPANY_ENABLED` включена. На проде выключено (legacy).

## 9. Пользователи, тарифы и платежи

### `app:tubus`

- **Класс:** `SyncUsersWithTubus`
- **Назначение:** синхронизация пользователей с внешним сервисом Тубус. Берёт до 30 пользователей с телефоном и без `tubus_id`, проверяет номер через `ApiTubus`, при необходимости связывает аккаунты и сохраняет `tubus_id` (при ошибке пишет `0`, чтобы не зациклиться).
- **Расписание:** да, ежечасно.

### `app:tariff:users`

- **Класс:** `CheckUserTariffs`
- **Назначение:** переводит активные тарифы пользователей с наступившей `date_end` в статус «завершён».
- **Расписание:** да, каждые 15 минут.

### `app:payments:check`

- **Класс:** `PaymentStatusCheck`
- **Назначение:** проверка статусов новых платежей в Robokassa (`opState`). Успех (код состояния 100) → платёж подтверждён; ошибка провайдера → статус «ошибка» с описанием; код 3 («оплата не найдена») считается допустимым и ожидается дальше; по истечении `Payment::PAYMENT_TTL` платёж помечается просроченным. Логи — канал `payments`.
- **Расписание:** да, каждые 2 минуты.

### `app:api_post_users:last_post_date`

- **Класс:** `SetLastPostDateToUsers`
- **Назначение:** пересчитывает `last_post_date` у всех `api_post_users` по дате последнего активного `Specialist`; если активных постов нет — обнуляет поле. Полный проход по таблице, разовая/сервисная операция.
- **Важно:** на порядок в публичных каталогах не влияет — с 07.09.2026 `/specialists` и `/builders` сортируются по дате последнего сообщения активных карточек своей витрины (`App\Support\CatalogLastMessage`).

## Команды в расписании (cron)

Расписание задаётся в `bootstrap/app.php` (`withSchedule`). Всё, чего нет в таблице, запускается только вручную.

| Команда | Периодичность | Примечание |
|---|---|---|
| `app:tg_parse:specialist` / `:builder` / `:company` | по настройке `read_source_cron`, иначе ежечасно | группа `madeline-proto`, `withoutOverlapping(180)` |
| `app:vk_parse:specialist` / `:builder` / `:company` | по настройке `read_source_cron`, иначе ежечасно | `withoutOverlapping` |
| `app:ai_parse:specialist` / `:builder` / `:company` | каждые 30 минут | одна группа без пересечений |
| `app:ai:health-check` | каждые 15 минут | |
| `app:ai:yandex-health-check` | каждые 15 минут | |
| `app:tubus` | ежечасно | |
| `app:tariff:users` | каждые 15 минут | |
| `app:payments:check` | каждые 2 минуты | |
| `app:tg_chat:send_company` | ежеминутно | только при `SCHEDULE_TG_CHAT_SEND_COMPANY_ENABLED=true` |

Значение настройки `read_source_cron` интерпретируется так: до 59 — каждые N минут; от 60 до 1439 — каждые N часов (округление вверх); больше — раз в сутки в 00:00.

## Типовые сценарии эксплуатации

**Переобработать посты строителей за период после правки промпта:**

```bash
php artisan app:ai_parse:requeue --type=builder --status=dontmatch --from=2026-08-01 --to=2026-08-31 --dry-run
php artisan app:ai_parse:requeue --type=builder --status=dontmatch --from=2026-08-01 --to=2026-08-31
```

**Починить пустые карточки в каталоге строителей:**

```bash
php artisan app:ai_parse:requeue-builder-missing-visible-posts --dry-run
php artisan app:ai_parse:requeue-builder-missing-visible-posts --apply --limit=200
php artisan app:ai_parse:builder
```

**Восстановить сессию Telegram после сбоя парсера:**

```bash
pkill -f "MadelineProto worker"
php artisan app:tg_auth --reset --qr
php artisan app:tg_parse:builder
```

**Массовая чистка каталога строителей от постов найма и проектирования:**

```bash
php artisan app:catalog:disable-active-builders-hiring-text --dry-run
php artisan app:catalog:redirect-non-field-builders-to-specialists --dry-run
```

## Регламент обновления документа

Документ поддерживается в актуальном состоянии вместе с кодом. При работе с `app/Console/Commands`:

1. **Новая команда** — добавить её в подходящий раздел (класс, назначение, опции, расписание, риски), обновить содержание при необходимости и счётчик команд в шапке.
2. **Изменение существующей** — синхронизировать сигнатуру, список опций и описание поведения; если команда попала в расписание или вышла из него — обновить таблицу cron.
3. **Удаление или переименование** — убрать раздел, а если команда была заменена другой, оставить упоминание о замене в описании преемника (как сделано для `app:ai_parse:reset-builder-queue` / `reset-specialist-queue` → `app:ai_parse:requeue`).
4. Обновить дату в шапке файла.
5. Значимые изменения дополнительно фиксировать в `DOC/CHANGE_LOG.md`.
